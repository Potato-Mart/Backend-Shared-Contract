# v38.1.0 capture timing adoption

This additive module release preserves `/v38` and the legacy `PaymentCapturedEvent` v1 Go/wire model. The new `pubsub/payments.PaymentCapturedEventV2` is the payload for `payment.captured` **event_version v2**. Wire compatibility is separate from module compatibility: receivers must explicitly support v2 before producers emit it. `Payment.CaptureTiming` is an optional shared persisted evidence projection; absence means timing is unknown. Payment `paid_at` is unchanged and must not be substituted for evidence.

## Exact v2 shape

All existing identity/amount/method/geography/request fields are retained. Top-level `captured_at` is replaced in v2 by required `capture_timing`:

```json
{"payment_id":"payment-1","order_number":"GC000000000001","amount":{"amount_minor":1000,"currency":"AUD"},"capture_timing":{"confirmation":{"upper_bound_at":"2026-09-29T03:00:01Z","source":"provider_event","provider":"stripe","evidence_reference":"evt_capture_1"}}}
```

`payment.CaptureTimingEvidence` contains:

| Field | Requiredness | Meaning |
| --- | --- | --- |
| `captured_at` | Optional pointer to timestamp | Actual exact capture time, only when an authoritative source establishes it |
| `confirmation` | Optional pointer to evidence | Authenticated proof that this amount had been captured no later than a conservative upper bound |

At least one is required for v2 by Payments validation. An empty object remains representable for historical unknown state but must not be emitted as authenticated timing evidence. If both exist, Payments checks consistency and provenance. Neither field is inferred from event envelope time, webhook receipt, local processing time, intent creation or charge creation.

`payment.CaptureConfirmationEvidence` contains four required fields: `upper_bound_at` (timestamp), `source` (`provider_event` or `provider_status_observation`), `provider` (provider identifier) and `evidence_reference` (opaque authenticated event ID or immutable observation ID). Payments stores protected source proof privately and verifies payment/provider/account/amount correlation before emitting evidence. No raw provider response, credential, customer data or delivery material enters this model. Existing payment-events transport is reused; no new topic is introduced.

## Deadline semantics owned by Orders

- An authoritative exact time at/before deadline proves in-time capture; an exact time after deadline proves late capture.
- A valid confirmation upper bound at/before deadline proves capture was in time.
- A confirmation upper bound after deadline does **not** prove late capture. Capture could have happened earlier; the outcome is ambiguous without stronger evidence.
- Missing timing evidence is unknown. Never fill exact capture time with processing/retry time.
- Delayed webhook, API sync and replay preserve the original immutable evidence. Later observations must not erase earlier stronger evidence.

Orders owns expiry/capture race handling and the ambiguous-result workflow. No deadline decision helper or runtime provider logic is included here.

## Stripe mapping and precision

Stripe documents [`Event.created`](https://docs.stripe.com/api/events/object) as event-object creation time and [`Charge.created`](https://docs.stripe.com/api/charges/object) as charge-object creation time. Its [manual-capture documentation](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method) separates authorization from capture. Consequently neither value establishes exact capture time.

A verified succeeded/captured provider event whose payload establishes the relevant captured amount can support confirmation evidence. Treat its event creation timestamp as an upper-bound source, with **precision accounted for**: Stripe timestamps are integer seconds, so use a conservative end-of-resolution bound (e.g. `Event.created + 1 second`, plus any required clock safety allowance), not the truncated start of that second. This avoids falsely proving capture before a deadline inside the same second. Source is `provider_event`; reference is its authenticated event ID.

For API sync, an authenticated provider result can establish that capture had succeeded by the observation completion time. Use `provider_status_observation`, preserve an immutable proof reference and account for clock precision/skew. This is observation evidence, never an invented exact capture time; a late observation remains inconclusive about the deadline. Payments owns the authentication, conservative bound construction and any provider-specific guarantees.

## Adoption and verification

Payments persists timing evidence and emits v2; Orders consumes it for gift deadlines, while Insights and Notification adopt the same event version without reinterpreting upper bounds as exact timestamps. Producers follow consumer readiness. Legacy v1 can be consumed for actual exact timestamps only; historical fabricated timestamps must not become trusted exact evidence. No database migration, backfill, reset or legacy conversion is supplied.

Tests cover absent exact time, confirmation-only JSON, distinct exact/confirmation timestamps, replay roundtrip, source enums, optional persisted evidence and unchanged v1 shape. Backend owns authenticated provider fixtures, precision/deadline boundary tests, delayed/replayed events, terminal/manual provenance and expiry/capture races.
