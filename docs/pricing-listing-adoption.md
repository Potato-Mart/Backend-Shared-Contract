# Pricing market-listing adoption

Use `github.com/Potato-Mart/Backend-Shared-Contract/v40 v40.0.0` in service modules and CI/build metadata. Replace every shared-contract Go import prefix with `/v40`; do not import both majors in the same service or retain migration casts, aliases, parallel listing records or mapping scaffolding.

Pricing is the sole owner of `pkg/contracts/pricing/listing.MarketListing` and `SaleRestriction`, with `MarketListingStatus` and `SaleRestrictionKind` in `pricing/listing/listing_enums`. These reuse the existing listing fields, optionality and enum values. Listings contain commercial availability and configuration references; authoritative price amounts remain in price books.

The duplicate `supply/catalogue/listing.MarketListing`, `SaleRestriction` and its `listing_enums` package are removed. The one `CatalogListingChangedEvent` definition is now under `pubsub/pricing`; its JSON fields, `catalog.listing_changed` type and existing topic/version semantics are unchanged. No old definitions, aliases or compatibility mappings are provided in `/v40`. The already published `/v39 v39.4.0` release remains immutable historical evidence.

Supply retains `supply/catalogue/listing.SaleEligibilitySnapshot` and `DamageSaleApproval`, DepotMarket, catalogue and physical inventory evidence. A file using both commercial listings and inventory evidence must use separate Pricing and Supply imports. Listing revision and tax-category references in stock evidence refer to Pricing authority; inventory revisions and validity tokens retain Supply meaning.

Supply and Pricing consume the removed models/enums and must adopt the canonical definitions directly. Pricing must also remove its `legacyEnums.MarketListingStatus` cast. Orders uses the retained Supply eligibility model and needs the module-major upgrade without moving that evidence. Identity, Customers, Payments, Notification and Insights also pin the shared module and must update module/import/build metadata together when adopting this major. Their owning chats perform service edits and verification; Contract writes stay in this repository.

Upgrade only after the verified release exists. Service owners then run their own CI gates with `GOWORK=off`, remove stale imports and compatibility scaffolding, and coordinate runtime listing ownership before cutover. No source listing-data migration is required by the user. Routes, DTOs, persistence, authorization, event publication and deployment remain service-owned. The module release alone does not establish completed service adoption or production readiness.
